# docs/DATA_MODEL.md

## Database Principles

- Supabase Postgres is the source of truth.
- Every exposed table has RLS enabled.
- Every owner-owned table includes `user_id` even though the product is single-user.
- Use UUID primary keys.
- Use JSONB for raw API payloads, AI reports, score metadata, capability flags, and flexible structured outputs.
- Use soft deletes for mutable owner content.
- Use append-only rows for audits, jobs, prompt runs, metric snapshots, and publishing failures.
- Encrypt OAuth tokens before persistence.
- Hash personal save tokens before persistence.
- Never store decrypted X tokens, AI keys, or service role key.

## Common Fields

| Field | Type | Rule |
|---|---|---|
| `id` | `uuid` | Primary key generated by database. |
| `user_id` | `uuid` | Required for owner-owned data; references `auth.users(id)`. |
| `created_at` | `timestamptz` | Default `now()`. |
| `updated_at` | `timestamptz` | Updated by trigger on mutable tables. |
| `deleted_at` | `timestamptz` | Soft delete for user content. |
| `metadata` | `jsonb` | Optional, never secrets. |

## Status Values

- Publishing draft: `draft`, `ai_generated`, `owner_edited`, `analyzed`, `approved`, `scheduled`, `publishing`, `published`, `failed`, `canceled`, `archived`.
- Blog: `idea`, `outlining`, `drafting`, `editing`, `ready`, `exported`, `published_externally`, `archived`.
- Job: `queued`, `running`, `succeeded`, `failed`, `canceled`.
- Experiment decision: `continue`, `stop`, `iterate`, `scale`.
- Confidence: `fact`, `inference`, `speculation`, `mixed`.

## Required Tables


### `profiles`

**Purpose:** Application profile for authenticated users.

**Required columns:** id uuid pk auth.users, email text unique not null, display_name text, avatar_url text, is_admin boolean default false, last_seen_at timestamptz, metadata jsonb. Also include `created_at timestamptz default now()`, `updated_at timestamptz default now()` where mutable, and `deleted_at timestamptz` for soft-deletable owner content unless the table is append-only.

**Indexes and constraints:**

- Primary key on `id`.
- Index `user_id` when present.
- Add unique constraints for natural identities where applicable: platform ids, usernames per owner, slugs per owner, idempotency keys, token hashes, active schedule rows.
- Add GIN indexes for `tags`, JSONB fields used in filters, and full-text searchable text fields.
- Add vector index on `embeddings.embedding` after enough rows justify approximate search.

**RLS:** Enable RLS. Owner policies require `auth.uid() = user_id`. Service-role writes are server-only. Generic embedding/search functions must explicitly filter by `user_id`.

**Lifecycle:** Create/update through server actions or route handlers after Zod validation. Preserve audit or job records append-only. Soft-delete user content; hard-delete only through data deletion.

**Audit behavior:** Audit when the table affects auth, tokens, external X writes, publishing approval, data export/delete, settings, or extension token operations.

## Migration Plan

1. Extensions: `pgcrypto`, `vector`, optional `pg_trgm`, updated-at trigger.
2. Identity/settings: `profiles`, `app_settings`, `audit_logs`.
3. X/read archive: `x_connections`, `posts`, `post_metric_snapshots`, `sync_jobs`.
4. Content intelligence: ideas, outputs, brain dumps, inspiration, targets, reports, voice profiles.
5. AI infrastructure: `ai_jobs`, `prompt_runs`, `embeddings`.
6. Publishing: drafts, jobs, scheduled posts, published posts, failures, media, calendar.
7. Blogging: blog posts, versions, exports, repurposing jobs.
8. Growth: goals, pillars, campaigns, experiments, reviews, profile audits.
9. Extension auth: personal save tokens.
10. RLS and policies for every table.

## Data Ownership

The owner owns all records. Exports must include all owner content except decrypted secrets. Data deletion must delete token material first, then dependent rows in safe order.

## Acceptance Criteria

- All required tables exist with indexes, constraints, and RLS.
- Cross-user reads/writes fail under anon/authenticated clients.
- Publishing state can be reconstructed from drafts/jobs/scheduled/published/failure rows.
- Blog version history can restore previous content.
- Experiment results can be traced to included content and metrics.
